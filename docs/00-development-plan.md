# 四阶段开发方案

## 实施约定

- 工作区：`D:\Desktop\小影笔试`。
- 当前阶段一至三完成；阶段三累计 85 项工程测试通过，10 个真实用例的最新结果通过本次核验，阶段四未开始，未创建远程仓库。
- 技术方向：Python CLI、原生有界 Agent 循环、本地 JSON 资料、独立模型适配器、pytest。
- 不开发界面、部署、多 Agent、权限系统或生产级向量库。
- 先确认真实模型可调用。若暂不可用，可以先做工具和 Mock，但必须保留“真实模型验收未完成”的状态。
- 四阶段按顺序实施；每阶段记录修改文件、验证结果、失败、实际用时和未完成项。阶段完成不等于整个项目验收通过。
- 阶段一至三表内模块已实现；阶段四模块仍为计划。阶段三提供原文来源校验和冲突保留机制，语义支持性仍需模型与结果复核，不能用字符匹配证明全部正确。

## 阶段一：资料与工具基础

**目标：**让知识源、检索、读取和测试场景可独立验证。

**计划模块：**

| 模块 | 计划路径 | 职责 |
|---|---|---|
| 数据结构 | `src/knowledge_agent/schemas.py` | 文档、工具结果、错误、输出字段与状态 |
| 场景装载 | `src/knowledge_agent/corpus.py` | 只装载指定场景文档，应用替换，形成固定语料快照 |
| 检索 | `src/knowledge_agent/retrieval.py` | 中文字符 n-gram、标题加权、同义归一化；保留简单匹配基线 |
| 工具 | `src/knowledge_agent/tools.py` | `search_docs`、`read_document` 和可控失败注入 |
| 基础测试 | `tests/test_corpus.py`、`tests/test_tools.py` | 场景隔离、检索、原文读取、错误结构 |

**实施顺序：**先验证数据结构和 ID，再实现显式场景装载，然后实现读取和检索，最后加入测试专用故障注入。先做最小模型连通检查，尽早暴露模型不可用问题；正式适配器在阶段二完成。

**完成门槛：**

- 基准场景不可访问 D02；冲突场景可同时召回 D01 和 D02。
- 文档 ID、日期、原文和片段位置可以核对。
- 45 天替换及条款删除均能改变装载后的语料；索引随语料重建。
- 同义问法能在有限候选中找到所需文档；检索无结果返回空结果而不是异常。
- 文档不存在、非法参数和注入失败返回规范错误。

**阶段产物：**可独立测试的数据与工具模块、基础测试结果。此阶段不能宣称 Agent 已实现。

## 阶段二：真实模型驱动的决策闭环

**目标：**实现“模型选择动作 → 执行工具 → 观察结果 → 调整下一步或结束”。

**计划模块：**

| 模块 | 计划路径 | 职责 |
|---|---|---|
| 模型适配 | `src/knowledge_agent/model.py` | 接入一种实际可用模型，隔离供应商差异 |
| 离线模型 | `src/knowledge_agent/mock_model.py` | 固定测试响应或受控响应，明确标为 Mock |
| 执行器 | `src/knowledge_agent/agent.py` | 动作分发、结果回传、证据状态、预算和异常处理 |
| 提示规则 | `src/knowledge_agent/prompts.py` | 工具用途、证据规则、冲突原则、允许的动作 |
| 记录 | `src/knowledge_agent/trace.py` | 每步动作、参数、结果摘要、简短依据和预算 |
| CLI | `src/knowledge_agent/cli.py` | 当前问题、可选历史、场景、模式及输出目录 |

**实施顺序：**先接入模型并验证结构化动作，再实现单工具循环，然后支持多步观察与结束，最后补预算、Trace、历史和 Mock。

**完成门槛：**

- 真实模型成功运行至少一条检索后读取原文的路径。
- 模型能观察到每次工具成功、空结果和错误，而不是执行器私自隐藏结果。
- 动作由模型输出；不得根据用例编号、场景名称或关键词直接返回业务答案。
- 最多 8 轮模型决策、6 次业务工具调用；修正、重试都消耗相应预算。
- 预算耗尽由执行器明确返回 `incomplete`，不额外无限调用模型。
- 模型/API 失败与业务工具失败可区分；不自动静默切换 Mock。
- Trace 不记录密钥或模型内部思维过程。

**阶段产物：**CLI 闭环、真实运行记录、Mock 入口、执行器测试。尚未完成证据和全部业务验收时，不标记项目完成。

## 阶段三：证据、冲突和边界场景

**目标：**保证回答受到本次读取证据约束，处理冲突、资料不足、追问和故障。

**计划模块：**

| 模块 | 计划路径 | 职责 |
|---|---|---|
| 证据状态 | `src/knowledge_agent/evidence.py` | 保存成功读取的原文快照、模型提取的规则与未解决冲突 |
| 引用校验 | `src/knowledge_agent/validation.py` | 核对 ID、版本、片段、位置和引用来源 |
| 输出展示 | `src/knowledge_agent/render.py` | 输出回答、引用、冲突、缺口、问题和状态 |
| 行为测试 | `tests/test_agent_contract.py` | 状态、非法引用、错误动作、预算和失败路径 |

**实施顺序：**先约束正式引用只来自已读原文，再实现冲突事实与查证规则，然后处理历史追问、资料外问题和失败后的决策，最后检查最终输出。

**完成门槛：**

- D01 / D02 同时存在且适用关系不明时，列出两份原文并请求确认，不选较新或较短期限。
- 仅有 D01 时可以依据 D01 回答 30 天。
- 国内与境外住宿标准按有据可查的适用范围区分；不能把不同范围误当作同一规则冲突。
- D12 的明确替代条款可以解决 D11 / D12 的版本差异；日期本身不能解决冲突。
- 资料外问题和删除关键条款后的问题不补造制度。
- 历史只帮助理解当前问题，旧回答不是当前引用证据。
- 不合法引用先反馈给模型修正，预算耗尽则返回未完成状态。
- 支持 T01—T06 的核心验收场景，并记录真实模型结果。

**阶段产物：**可核验的回答、边界处理测试、正常/不足/故障三类实际记录。

## 阶段四：效果验证、改进与提交

**目标：**用实际结果证明动态行为、证据依赖与可复现性，完成仓库交付。

**计划模块与材料：**

- `tests/test_acceptance.py`：评估工程约束；真实模型验收需显式启用并与离线测试分开。
- `scripts/evaluate.py`：装载评估用例、运行、归档结果；不得把标准答案传给模型。
- `examples/`：输入、输出、Trace、测试结果和检索改进前后对比。
- README、依赖文件、`.env.example`、`.gitignore` 和五份必交文档。

**实施顺序：**先完成必测场景，再做文档替换、冲突新增、证据删除及上限测试；比较检索基线与改进版；修复关键缺陷；最后验证安装命令和提交信息。

**完成门槛：**

- 六项题目验收全部有预期、实际结果和可定位的 Trace。
- 至少三组完整输入/实际输出/Trace 覆盖正常、资料不足、工具失败。
- 至少两条真实模型路径体现工具结果改变后续动作，而不是预设路径日志。
- 资料内容替换会改变答案；新增冲突会改变动作或最终状态；删除依据后不复用旧答案。
- 检索改进报告使用同一组问题、同一语料，注明数据场景和版本。
- 错误引用、无依据回答属于阻断提交的关键缺陷；不得用平均分掩盖。
- 记录真实模型、模型标识、实际依赖版本、调用参数、失败、限制及实际用时。
- README 的安装和运行步骤经验证，最后填写题号、GitHub URL、最终 commit SHA；私有仓库评审访问可用。
